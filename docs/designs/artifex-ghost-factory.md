## Problem Statement

Coding with agents (Muse, Claude Code, Codex, OpenCode) is powerful but opaque: plans live in chat, files change in a list, and understanding how a repo fits together requires re-reading files. Artifex makes a repo legible as a live factory floor — files/modules as buildings, static imports as belts, a database zone showing schema (tables and which modules read/write them; v1 shows no stored row data), and one v1 worker agent whose intent and progress are visible where the agent can emit them — so the builder can see structure, watch a change land, ask the worker what it is doing and why when it supports questions, and steer without first rebuilding a mental model from text. In v1 a "backed-up belt" means import-structure congestion only (a heavily imported or changed area worth inspecting), never a runtime performance claim; runtime bottleneck overlays are a later layer. First user is the builder himself; then a vibe coder; a non-technical viewer is the comprehension test.

## What Makes This Cool

- Ghost blueprints for agent plans: intended files appear translucent and solidify as the agent writes them, so you watch intent become a system (the plan-then-files-spawning moment the builder already loves). Observed-only agents (no intent events) never get ghosts: their buildings appear fully solid with an "observed" badge and a change pulse, visually distinct from a solidified ghost.
- Agents are the main attraction: a live worker you can talk to ("what are you doing, why?") when the agent supports it, not a chat box beside an editor. When it does not, the floor says so plainly (see capability matrix).
- Structure you can see at a glance: import belts, change pulses, and test state make "what connects to what, what just changed, what broke" visible on the floor instead of hidden in logs. Performance bottlenecks join this view only when runtime metrics exist (later layer).

## Constraints

- Potato-first: low RAM and low compute from day one; must stay usable on the target weak machine defined under Success Criteria. No heavyweight shell, no always-on heavy indexing.
- Text stays the source of truth: the factory reads and reflects real files and reflects DB schema (v1: schema only, read-only, no stored rows); it does not replace code with a graph language.
- Any agent should be comfortable on the floor: Muse first for the daily loop, with Claude Code / Codex / OpenCode to follow; the floor exposes the agent-facing interface defined below so agents query state directly instead of screen-scraping.
- Safety (v1 contract): server binds to 127.0.0.1 only with a per-launch random token required by the browser tab (token never in URLs or logs; Origin and Host headers validated, WebSocket policy stated, per eng review D18); DB connects only after a confirm step naming the host, uses a read-only transaction for schema introspection, takes credentials only from the repo's existing environment/config at launch, and never stores them; file and schema display masks values matching common secret patterns (keys, tokens, passwords) and never renders `.env` contents as data; agent annotate text is escaped and secret-masked before rendering.

## Premises

1. Text is truth; the visual factory is a live map and control floor over real files and a real DB (schema in v1).
2. Agents are first-class users; humans manage, agents work.
3. Potato-first is a hard constraint that shapes every tech choice.
4. First value is seeing, then steering: see the repo and watch a change land before drag-to-rewire editing or a reusable-parts inventory.

## Approaches Considered

### Approach A: Watcher Map (minimal viable)

Local service renders one repo (folders, files, import belts) and highlights live changes while the agent runs in its normal terminal. No agent API needed. Effort S, risk low. Its ground layer and event log are built as part of B, not discarded.

### Approach B: Ghost Factory (ideal architecture) — CHOSEN

Agent-native floor: structured plan/tool events render as ghost buildings that solidify as files land; the map is exposed back to agents so they plan in the shared space; prompt and ask-why happen on the floor for agents that support them. Effort L, risk medium-high, gated by the protocol spike below. V1 is single-agent (one active worker); multi-agent floors, collision handling, and change attribution across concurrent agents are later work, and v1 copy uses singular "worker" framing.

### Approach C: Replay Theater (creative/lateral)

Record each agent session as a scrubbable timeline (intent, files, dependencies, test results) for study and debugging. Deferred as a layer on the B event log rather than the first build.

## Recommended Approach

Build B, gated by a protocol spike and a validation gate. Rationale: the builder chose the agent-native version explicitly — agents comfortable on the floor is the differentiator, and ghosts make the beloved plan-to-files moment a product feature instead of a side effect.

Protocol spike (gates ghost scope): time-box 2 working days. Per agent, the spike labels each capability separately (per eng review D6): emits-intent (plan/intent files it will touch, through a documented adapter such as ACP or an equivalent CLI/stream), file-written events, receives-prompts, answers-why (short "what/why" for its current step), or observed-only. Ghost scope is keyed only to emits-intent with measured path-before-write lead time (eng review D11: spike records lead time and planned-vs-written match rate per agent; an agent whose paths arrive only at write time is labeled observed for ghost purposes). The spike records a capability matrix before any ghost UI is built:

| Capability | Meaning | If absent, user sees |
|---|---|---|
| Emits intent | Plan/tool events arrive before or as work happens | No ghosts; buildings appear solid with "observed" badge on filesystem change |
| Receives prompts | Floor prompt box can start/steer a session | Prompt box disabled for that agent with "run this agent in its terminal; Artifex will observe" |
| Answers why | Agent returns what/why for current step on request | Building panel shows last observed file changes and diff only, labeled "agent cannot be asked" |
| Observed-only | Filesystem watching is the only signal | All changes labeled observed, never presented as intent |

Both-fail rule (eng review D12): if no tested agent emits paths before writes with usable lead time, v1 ships the live map plus agent interface without ghost UI. Decision rule if Muse fails the spike: if Muse is observed-only while Claude Code passes, the builder chooses at the gate between (a) accept Muse observed-only as the daily loop with ghosts only from Claude Code, or (b) make Claude Code the v1 primary agent. Ghost scope is not built for an agent that cannot emit intent; Approach A behavior is the floor for that agent. No silent fallback: the matrix ships in the README and in the floor's agent picker.

Spike outcome (2026-10-13, `spike/RESULTS.md`): no agent emits paths before writes naturally (write-time only: Muse none, Claude Code 52 ms, Codex 20 ms — all observed for ghost purposes per D11). Elicited intent works on both gate agents: Muse via a standing todo instruction (`todo.snapshot.updated`, median lead 29 s, planned→written 3/3) and Claude Code via plan turn → approve → resume (4/4). D12 both-fail does not trigger; ghost scope ships as elicited intent, everything else observed-solid. Codex is partial (natural-language plan steps via app-server, no live path lead); OpenCode is unverified (no provider credentials on the spike machine; ACP handshake verified). Muse stays the v1 primary — the Muse-fail choice does not trigger because Muse passes when elicited. D14 baselines recorded in `spike/RESULTS.md`: empty Bun 22.5 MiB, grammar-loaded parser ~66 MiB by `ps`, and a direct five-process measurement of 155.7–156.0 MiB at synchronized idle (211.7–216.7 MiB after a full parse) — the five Artifex-owned units as separate Bun processes cannot fit the 150 MB budget, so per D14 the arrangement folds to one Bun process (in-process modules, parser in-process or worker thread), same features. Builder gate inputs recorded 2026-10-13 (see `spike/RESULTS.md`): weak machine is this Mac (Apple M4 Pro, 24 GB, macOS 27.0.1), browser-tab fail threshold 500 MB (D15), solo effort budget recorded as no fixed cap (builder decision; the D21 gate reviews scope qualitatively). Still open: OpenCode provider login + harness rerun.

Agent-facing interface (v1 minimal contract): local MCP-style server on 127.0.0.1 (same launch token as the UI; bootstrap per eng review D19: 0600 token file under .artifex/ plus a printed connect snippet per agent) exposing read queries `floor.listBuildings`, `floor.getBuilding(path)` (imports, dependents, recent changes, test state), `floor.getPlan` (current ghosts and their state), and `floor.getDbSchema`, plus one allowed action in v1, `floor.annotate(building, note)` (agent leaves its why-note on a building). Agents may not write files through this interface in v1 (file writes stay in the agent's own tools, observed as ground truth); auth is the launch token, bound to localhost only.

Ground-layer contracts (v1): languages committed to TypeScript/JavaScript + Python; belts cover static relative imports plus absolute imports resolved against repo/package roots and tsconfig paths (eng review D13; deterministic, never guessed; barrel re-export chains beyond one hop and dynamic `import()` / Python dynamic imports are unresolved: omitted from belts and counted in a per-building "unresolved imports" note, never drawn as guessed belts). Layout committed to folder-zone packing mirroring directory structure (folders as fenced zones, files as buildings sized by line count). Filesystem behavior: deletion removes the building with a fade and a change-log entry; rename is a move (building keeps identity by path change event); parse failures show a cracked-building badge with the parser error on click; binary files render as small unlabeled blocks (size by bytes bucket, no line count); files over 5,000 lines are capped in display size with true line count in the panel; ignore rules follow `.gitignore` plus hard-excluded `node_modules`, `.git`, and build output; watcher overflow or missed events trigger a full rescan reconciliation (diff disk vs floor, then correct silently and log it).

Stack starting point (to be locked in eng review): Bun/TypeScript local server on localhost in a browser tab (Tauri later, no Electron), tree-sitter (WASM) parsing for TS/JS and Python, Canvas2D rendering, filesystem watch for ground truth.

Validation gate: after ground + ghost layers (Next Steps 1–4), the comprehension test and potato check must pass before prompt/talk polish and the DB zone proceed. Seeing is validated before steering scope grows, per Premise 4. Gate authority (eng review D21): a failed gate stops later scope until a recorded descope-or-stop decision; remaining work is reviewed against the solo effort budget recorded at spike end.

## Open Questions

- DB engines for the v1 schema zone: SQLite + Postgres, or SQLite only first? (Behavior is committed to schema-only; engine list is the open part.)
- Multi-repo projects: v1 opens a single repo. Federating several repos on one floor (repos as districts, cross-repo belts from API/contract links) is deferred; decide after the single-repo floor passes its gate. (Raised in eng review D5.)

## Success Criteria

- Comprehension test (protocol per eng review D5): builder names one small real repo (about 20 files) before the gate; a non-technical viewer answers 3 fixed questions from the map alone (what does it do, what just changed, where would X live); pass is 2 of 3 correct within 2 minutes without opening files. Control per eng review D16: same questions on a plain file tree, X picked by someone other than the builder; both results reported.
- Daily loop: builder opens a real repo, prompts the agent, and watches ghost-to-solid (or observed-solid, per matrix) land in the right buildings without opening a file list.
- Potato check (pass/fail): target weak machine is the builder's lowest-spec available machine, recorded by name/spec in the repo before measuring. Pass = Artifex-owned processes (server, parser, watcher, interface, DB introspector) at or under 150 MB total with per-unit numbers recorded, and near-zero idle CPU (under 2% sustained) on a ~1,000-file repo (dependencies and generated output excluded); browser tab memory measured against a stated fail threshold (threshold value recorded with the named machine spec before the gate run); numbers recorded in the repo either way. (Amended by eng review D3 and D15.)
- Agent comfort check: an agent answers "what exists, what is planned, what changed" using only the agent-facing interface (no screen-scraping) in a scripted trial.

## UI Spec (design review)

Layout and hierarchy (design D3): three regions plus status. Canvas fills the viewport (the one visual anchor). Persistent top strip answers "what is the worker doing right now?" (agent, current building, current step, test state). Single right inspector shows one selected thing at a time. Bottom prompt bar holds the prompt and agent picker. 24px status strip carries N of M buildings and watcher state. DB zone is a region on the canvas, not a modal. The worker is the protagonist: the floor exists to give its actions context. At rest, at least 80% of buildings are visually quiet; only ghosts, the active building, and recent change pulses compete.

Encoding table (design D4): each visual channel has one meaning. Fill = provenance (solid existing; translucent plus dashed ghost planned; solid with observed treatment for observed-only changes). Outline = health (cracked parse error, dashed abandoned). Motion = recency only (change pulses). Badges live in the inspector, not on the canvas. States are distinguishable without color alone. A persistent legend ships in-product: open on first run, collapsible, one click to reopen; the comprehension test runs with it available but unpointed-to.

Belt rules (design D5): belts are zoom-gated. Far zoom shows aggregated zone-to-zone belts only; mid zoom shows major belts; near zoom shows all. Hover or selection isolates one building's in/out belts. Congestion means top-decile importer count with one outline treatment from the encoding table. Folder-collapsed mode uses rollup belts between zones.

Zone captions (design D6): each folder zone carries one plain-language sentence shown at mid zoom, drafted from the README or by the worker agent, rendered as a draft until the builder accepts it, editable in place. Captions answer "what does it do" for non-technical viewers.

Interaction states (design D7): one state table covers floor, DB zone, building inspector, and prompt bar across loading, empty, error, success, and partial. Loading past a short threshold explains what is still running (WASM parse, rescan, DB introspection, agent handshake). Watcher rescan corrections announce or animate, never silently rearrange a floor being read. Empty states carry warmth, context, and one primary action (first run: "Open a repo"). One degraded grammar (single muted, hatched treatment with evidence on click) covers observed buildings, inferred DB links, and unresolved imports. Every error names what happened, what still works, and one recovery action. Masked secrets render as a consistent masked token with a reason tooltip. Test state shows as a building mark plus a floor-level pass/fail summary in the top strip; prompt, annotate, and DB actions get transient confirmations.

First run (design D8): scripted opening. Zones on the recent-activity path start expanded (one-time unfold), a sample prompt is pre-filled when the agent supports prompts, and observed-only capability is framed as a gain ("you will see every change land live"), never as a disabled control. Intended feelings: minute 1 orientation, minute 5 first ghost, minute 30 ownership of a floor that explains itself.

Worker activity (design D9): top strip carries one calm worker state (thinking, writing, testing, waiting on user) mapped from agent tool/file events, plus a last-activity age. Abandoned never renders without the age shown first and a one-click keep-waiting action. Observed-only sessions derive the same readout from file activity.

Motion budget (design D10): ghost-to-solid is the only full-fidelity animation. Change pulses decay in under 1.5 seconds and cap at the 20 most recent. Idle means zero animation. prefers-reduced-motion collapses transitions to instant state changes with identical information. Finish stays flat blueprint: 1px lines, muted dark surfaces, one saturated accent for agent activity; no gradients, glows, or textures.

Tokens and type (design D11): CSS variables only, no hardcoded hex in components. Surfaces: graphite surface-0 (canvas), surface-1 (zones and bars), surface-2 (inspector). One line color. Text: text-primary and text-muted tinted from the surface hue, never gray. Accents: one activity accent reserved for the live worker, amber only for abandoned and inferred, red only for errors. Type: Instrument Sans for UI, JetBrains Mono for paths and code, tabular numerals for counts. Selection, focus rings, caret, and scrollbars are themed from the same palette. This seed feeds a later design consultation for a full DESIGN.md.

Amendment (2026-10-13, builder evidence after T3a shipped): the flat-blueprint finish in D10 was built and judged in person as "underwhelming, little to no Factorio-ish, point unclear." Superseded in part: buildings now render as Assembler Floor machines (beveled roof, status lamp = parse health, drop shadow, kind glyphs), zones as nameplated production pads, floor seams plated, first-run camera lands on recent activity (D8), and the top strip carries a last-change readout (D9 without an agent yet). What survives unchanged: one-meaning encodings (D4), motion budget, tokens-only styling (two tokens added: surface-3 roofs, hazard nameplate tab), red only for errors. Recorded so the DESIGN.md consultation starts from the shipped skin, not the superseded one.

Access and zoom (design D12): semantic zoom in three bands (far: zone names and captions; mid: labels for largest and recently changed buildings; near: all labels), with a minimum label-legibility rule at default zoom. Search-and-jump by path, arrow-key traversal, and the inspector mirrors selection as DOM text (the screen-reader surface). Narrow windows collapse the inspector to a toggleable overlay. Body text contrast at least 4.5:1, touch targets at least 44px, states never color-only.

Layout stability (design D13): buildings keep coordinates across sessions. New files append inside their zone, deletions leave gaps, zone growth expands outward, and nothing moves except on an explicit user relayout command. Persisted coordinates are versioned floor state.

Building size (design D14): stepped footprint buckets (four bands by line count; binary files map into the same bands by bytes). True line and byte counts live in the inspector. No height encoding.

Camera (design D15): follow-until-touched. The view tracks worker activity by default, yields instantly on user pan or zoom, and re-engages from a follow-worker toggle in the top strip. A compact minimap shows zone outlines and worker position. Camera moves obey the motion budget speed limits.

Conversation (design D16): one session thread in the bottom prompt bar. Why-answers render in the inspector for the selected building, newest pinned to the worker until selection changes. Prompts and answers persist in the event log (retention open question resolved: persist with the log, under the safety masking rules).

Inspector order (design D17): fixed order Why, Changes, Structure, Health; sections without data are hidden. Building name and true counts stay pinned at top as DOM text.

DB zone placement (design D18): fenced district at the floor edge on the same canvas. Module-to-table belts read as supply lines into the district and share layout stability, zoom bands, and zone captions.
